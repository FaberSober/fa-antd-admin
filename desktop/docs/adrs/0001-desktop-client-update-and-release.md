## 2. 背景与问题

Desktop 客户端需要支持版本检查和自动更新。当前 Desktop 已有运行时版本配置，但还没有安装包发布记录、平台安装包管理、更新清单接口和 Tauri 更新能力。

现有 `fa-app` 已有 Android APK 管理功能，适合作为管理端和发布流程参考；但 Android APK 的字段、解析和业务逻辑不能直接用于 Windows、macOS、Linux 安装包。

## 3. 决策

### 3.1 版本管理放入 `fa-app`

- 在 `fa-app` 增加 Desktop 客户端版本发布子模块。
- `fa-base` 只继续提供通用文件存储能力。
- `fa-core` 不增加客户端版本业务表或发布逻辑。
- 不修改现有 `Apk`、`ApkVersion` 的语义，避免 Android 与 Desktop 耦合。

建议的后端领域对象：

- `ClientApp`：客户端应用，例如 `faber-desktop`。
- `ClientRelease`：某个客户端的版本、渠道、说明和发布状态。
- `ClientReleaseArtifact`：版本对应的操作系统、CPU 架构、文件和签名。

### 3.2 使用动态更新接口，不要求专用 Nginx

Desktop 使用 Tauri Updater 的动态更新服务器模式。后台接口根据客户端请求选择适配的已发布安装包，并返回 Tauri 要求的更新清单。

建议接口：

```text
GET /api/app/client/update/{clientCode}
```

接口需要识别：

- 当前版本。
- 平台和 CPU 架构。
- 更新渠道，第一阶段只实现 `stable`。

无可用更新时返回 `204`；有更新时返回：

```json
{
  "version": "1.2.0",
  "notes": "修复文件上传异常，优化启动速度",
  "pub_date": "2026-09-16T10:00:00Z",
  "url": "https://api.example.com/api/app/client/download/123/windows-x86_64",
  "signature": "BASE64_SIGNATURE"
}
```

更新接口和安装包下载不能依赖普通用户登录，因为客户端可能在登录前检查更新。管理端的创建、上传和发布操作仍然需要管理员权限。

### 3.3 安装包下载层可按部署规模替换

第一阶段允许由 Spring Boot 直接提供受控下载，以减少基础设施和开发成本。下载层不是版本管理的核心，可以按需替换：

- 内部或小规模使用：后端直接下载。
- 正式环境：后端管理元数据，对象存储提供文件。
- 大文件或高并发：对象存储、CDN 或 Nginx 分发。

下载地址应通过专用公开下载接口校验版本发布状态，或使用短期对象存储签名 URL。可以复用 `fa-base` 的文件存储记录，但不直接把管理接口作为长期公开下载协议。

### 3.4 使用 Tauri 官方 Updater 并强制签名

- Desktop 接入 `@tauri-apps/plugin-updater` 和对应 Rust 插件。
- 在 Tauri 配置中设置更新公钥和更新接口。
- CI 构建各平台安装包并生成签名文件。
- 私钥不得提交仓库或写入 `.env`，只允许通过 CI 安全变量提供。
- 客户端内置公钥，拒绝签名不匹配的安装包。

Tauri Updater 的更新签名是必需的，Nginx、HTTPS 或后端权限不能替代安装包签名。[Tauri Updater 官方文档](https://v2.tauri.app/plugin/updater/)

## 4. 功能开发说明

### 4.1 统一版本号

- 以 `desktop/src-tauri/tauri.conf.json` 的版本作为发布基准。
- 保证 Cargo 包版本、前端运行时 `versionName` 和更新记录保持一致。
- `versionCode` 使用单调递增值，避免低版本被错误识别为新版本。
- 发布脚本或 CI 负责注入版本，避免多个文件长期手工维护不一致。

### 4.2 Desktop 版本管理后端

- 在 `fa-app` 中增加独立的 Desktop 客户端发布目录、Entity、Mapper、Biz 和 Controller。
- 版本和安装包分开建模，一个版本可关联多个平台架构包。
- 按项目规范分别提供 MySQL 和 PostgreSQL DDL。
- 记录草稿、已发布、已下线状态。
- 发布时校验版本号、平台包、签名和必要字段。

### 4.3 管理端版本维护页面

- 提供客户端版本列表和版本详情。
- 支持创建草稿、上传平台安装包、填写签名、编辑发布说明。
- 支持发布和下线，不允许直接修改已发布版本的核心安装包信息。
- 第一阶段不实现复杂灰度规则和审批流。

### 4.4 更新清单和下载接口

- 更新接口只返回已发布且高于当前版本的记录。
- 按平台和架构精确匹配安装包，找不到匹配包时返回无更新或明确错误。
- 下载接口只允许访问已发布版本的有效安装包。
- 对公开接口增加限流和基础审计日志。
- 下载次数统计可以先做简单累计，详细下载分析留给后续版本。

### 4.5 Desktop 更新能力

- 增加更新服务，封装检查、下载、安装和错误处理。
- 在首页或设置区域提供“检查更新”入口。
- 第一阶段不强制登录后才能检查更新。
- 下载完成后由用户确认重启安装。
- Windows、macOS、Linux 的安装和重启差异由 updater 插件处理，页面只展示统一状态。

### 4.6 发布与签名

- CI 按目标平台和架构构建安装包。
- 使用 Tauri signer 生成 `.sig`，并将签名内容写入版本安装包记录。
- 发布前检查每个平台的安装包和签名是否匹配。
- 正式版本必须经过人工确认后才切换为已发布。
- Tauri 官方发布文档建议将应用版本作为发布配置的一部分，并对各平台安装包进行签名。[Tauri 发布文档](https://v2.tauri.app/distribute/)

### 4.7 Telemetry

- 复用当前 Desktop Telemetry 上报能力。
- 记录更新检查结果、发现版本、下载失败、安装失败和安装完成等事件。
- 事件中包含客户端版本、目标版本、平台、架构和渠道。
- 不上报安装包内容、签名私钥或敏感下载凭证。
- 更新上报失败不能阻断正常客户端使用。

## 5. 非目标

第一阶段不包含：

- 专用 Nginx 静态发布目录。
- 多渠道灰度、按用户分组发布。
- 强制更新和最低版本拦截。
- 自动回滚和复杂审批流程。
- 离线安装包管理。
- 在客户端内保存更新私钥或其他发布密钥。

## 6. 验收标准

- 管理员可以创建 Desktop 版本并上传至少一个平台安装包。
- 管理员可以发布和下线版本。
- 客户端请求无更新时得到 `204`。
- 客户端能根据平台、架构和当前版本得到正确更新清单。
- 未登录客户端可以获取更新清单和安装包。
- 篡改安装包或签名不匹配时，客户端拒绝安装。
- 下载、安装和重启失败时有可理解的错误提示。
- 版本检查、下载和安装结果能够进入现有 Telemetry。
- 不影响现有 Desktop 登录、Telemetry 和 Demo 功能。
- MySQL 与 PostgreSQL 的后端 DDL 分目录维护，语法不混用。

## 7. 实施顺序

1. 确定版本字段、状态和平台架构枚举。
2. 在 `fa-app` 增加 Desktop 客户端、版本和安装包后端模型及 DDL。
3. 完成管理端版本维护和安装包上传。
4. 完成公开更新清单接口和受控下载接口。
5. 接入 Desktop Tauri Updater、权限和公钥配置。
6. 完成 CI 安装包构建与签名。
7. 完成客户端检查更新、下载、安装和提示交互。
8. 增加更新链路验证和 Telemetry 事件。
