# Mobile App Update Integration Implementation Plan

> **For Codex:** 按任务顺序执行；每个任务完成后先做对应验证，再进入下一任务。

**Goal:** 将 `mobile/` 的 App-PLUS 版本检查、增量 WGT/完整 APK 更新流程与 `fa-app` 的公开版本检查接口稳定联通，并形成可发布、可回滚、可验证的闭环。

**Architecture:** 复用 `fa-app` 已有的公开接口 `POST /api/app/app/release/check`，客户端只提交应用短码、平台、当前 `versionCode`、渠道和设备标识。`fa-core-mobile` 负责版本检查、下载、摘要校验、安装锁和平台安装能力；`fa-base-mobile` 负责生命周期触发、更新提示、强制更新和失败提示，业务页面不直接调用 `plus.runtime`。

**Tech Stack:** uni-app Vue 3 + TypeScript + `uni.request`/`uni.downloadFile` + App-PLUS `plus.runtime.install`；Spring Boot + MyBatis-Plus `fa-app` 发布模型；MySQL/PostgreSQL 既有 `app_release`、`app_release_package` 迁移脚本。

---

## 当前基线与范围

已存在且应复用的实现：

- `fa-app/src/main/java/com/faber/api/app/release/rest/AppReleaseController.java` 已提供无需登录的 `POST /api/app/app/release/check`。
- `fa-app/src/main/java/com/faber/api/app/release/biz/AppReleaseBiz.java` 已实现已发布版本过滤、版本号比较、渠道、灰度设备、最低支持版本、WGT 基准匹配和完整包回退。
- `mobile/src/features/fa-core-mobile/update/index.ts` 已实现检查、下载、SHA-256 校验、安装锁、WGT 安装和 Android 完整包安装。
- `mobile/src/features/fa-base-mobile/api/update.ts` 与 `common/update.ts` 已实现接口适配和弹窗流程，`pages/home/index.vue` 已在用户加载成功后触发一次检查。

本次执行默认以 App-PLUS Android 首次闭环为主；微信小程序继续使用 `uni.getUpdateManager`，H5 继续使用 CDN 清单，不把它们改为 WGT 流程。旧的 APK 历史接口和 Desktop 客户端更新接口不改动。通用 `app_release` 管理页面不纳入本次移动端接入；若不补管理页面，测试发布记录通过现有管理 API 或数据库初始化/运维脚本准备。

## 接口契约

请求：

```text
POST /api/app/app/release/check
{
  "appCode": "app_apk.short_code",
  "platform": "APP_PLUS",
  "currentVersionCode": 100,
  "channel": "stable",
  "deviceId": "持久化的客户端设备标识"
}
```

响应的 `data` 为 `AppReleaseCheckRet`：`hasUpdate`、`updateType`（`NONE`/`WGT`/`FULL`）、目标版本、`baseVersionCode`、`forceUpdate`、`downloadUrl`、`size`、`sha256` 和 `releaseNote`。客户端只有在 `hasUpdate=true` 且清单字段完整时才下载；下载后必须再次校验摘要，失败时保留当前版本并允许继续使用。

## 执行任务

### Task 1: 固化环境、版本和发布数据前置条件

**Files:**

- Modify if needed: `mobile/.env.example`
- Modify if needed: `mobile/src/env.d.ts`
- Modify if needed: `mobile/src/app.config.ts`
- Release metadata: `mobile/src/manifest.json` and the deployment-specific `mobile/.env.production.local` (ignored, never commit secrets)
- Reference: `mobile/docs/handbook/android-apk-release.md`
- Backend migrations to verify: `fa-app/src/main/resources/sql/fa-app/mysql/1.0.6_app_ddl.sql`, `fa-app/src/main/resources/sql/fa-app/mysql/1.0.8_app_ddl.sql`, and PostgreSQL counterparts

**Steps:**

1. Confirm the target `app_apk.short_code` and set it as `VITE_APP_UPDATE_APP_CODE`; keep `VITE_APP_UPDATE_CHANNEL=stable` unless a separate channel is intentionally published.
2. Keep `VITE_APP_VERSION_NAME`/`VITE_APP_VERSION_CODE` exactly aligned with `mobile/src/manifest.json`; increment `versionCode` monotonically for every native build.
3. Confirm the target environment has the `app_release`/`app_release_package` tables and that the file download URL generated by `FileSaveBiz` is reachable from the App device over HTTPS or the approved test network.
4. Prepare one published `APP_PLUS` release with either a matching WGT (`baseVersionCode=currentVersionCode`) or a `FULL` package. The release must contain a 64-character SHA-256 and a non-empty file ID.

**Expected result:** a real App build has a non-empty app code, a valid numeric current version, and a backend release record that can return a complete update manifest.

### Task 2: Verify and, if necessary, tighten the mobile API adapter

**Files:**

- `mobile/src/features/fa-core-mobile/update/types.ts`
- `mobile/src/features/fa-core-mobile/update/index.ts`
- `mobile/src/features/fa-core-mobile/update/device.ts`
- `mobile/src/features/fa-base-mobile/api/update.ts`
- `mobile/src/features/fa-core-mobile/common/request.ts`

**Steps:**

1. Confirm the client path resolves to `/api/app/app/release/check` for H5 proxy and for an absolute App API base URL.
2. Confirm Java `Long` values are validated as safe numeric `versionCode` values on the client; reject incomplete manifests, unsupported update types, invalid WGT base versions, empty URLs, and malformed SHA-256 values before downloading.
3. Keep the update check public and independent from login; do not add a second request client or a second WebSocket connection. Preserve existing common request telemetry and header behavior.
4. Confirm relative and absolute `downloadUrl` values both resolve correctly, and that download progress is clamped to `0..100`.
5. Confirm WGT installation uses `plus.runtime.install`, while full package installation is restricted to supported Android App-PLUS devices and gives iOS/unsupported platforms a store or enterprise-distribution message.

**Expected result:** the adapter consumes exactly the `fa-app` response contract and never installs an unverified or unsupported package.

### Task 3: Align update triggering and user interaction

**Files:**

- Current integration: `mobile/src/features/fa-base-mobile/common/update.ts`
- Current entry point: `mobile/src/features/fa-base-mobile/pages/home/index.vue`
- Host lifecycle candidate: `mobile/src/App.vue`
- Optional manual entry: `mobile/src/features/fa-base-mobile/pages/mine/about/index.vue`

**Steps:**

1. Decide the trigger policy before editing: the recommended policy is one check after app startup/foreground with an in-flight guard and a short cooldown, while keeping the current home-page fallback for the first authenticated session if the host lifecycle is not changed.
2. Avoid duplicate checks caused by `onShow`, `onActivated` and `onMounted`; retain one shared in-flight guard and do not let a stale page instance trigger a second download/install flow.
3. Keep optional updates dismissible, make `forceUpdate` hide the cancel action, and keep update notes visible in the prompt.
4. Add or complete the About page only if a user-facing manual check is required: display app name/version/versionCode from `APP_CONFIG` and expose “检查更新” using the same `checkAndPromptUpdate` service rather than duplicating request logic.
5. Preserve the existing Mini Program and H5 branches. They must not call WGT installation APIs.

**Expected result:** the update check runs at the agreed lifecycle point exactly once per intended check window, prompts safely, and behaves consistently for optional and forced updates.

### Task 4: Add focused backend/client contract coverage

**Files:**

- Backend test location: `fa-app/src/test/java/com/faber/api/app/release/` (add focused release-selection tests if the existing test setup permits)
- Mobile validation surface: `mobile/src/features/fa-core-mobile/update/` and `mobile/src/features/fa-base-mobile/`
- Do not modify old APK endpoints solely for this integration.

**Backend cases:**

1. Equal or higher current version returns `NONE`.
2. Draft and revoked releases are never returned.
3. Channel and app short code are respected.
4. Matching APP-PLUS WGT is preferred.
5. WGT base mismatch falls back to a FULL package.
6. A client below `minSupportedVersionCode` receives a forced FULL update.
7. Rollout/device targeting is stable, and an ineligible client receives `NONE`.

**Mobile cases:**

1. A valid response reaches `AVAILABLE`, downloads, verifies, and reaches `READY`.
2. Incorrect SHA-256 reaches `FAILED` and does not install.
3. A missing/invalid manifest is rejected before download.
4. Concurrent install attempts are blocked by the install lock.
5. Download, install, unsupported-platform, and user-cancel paths close loading UI and do not invalidate the current app.

**Expected result:** contract behavior is covered either by focused tests or, where the current mobile project has no test runner, by a documented HTTP/device smoke matrix rather than by adding an unrelated test framework.

### Task 5: Run staged verification and real-device smoke tests

**Commands:**

```powershell
pnpm --dir mobile type-check
mvn -pl fa-app -am -DskipTests compile
```

For an App-PLUS change, additionally run the repository-supported App build and test the generated package on Android; use the command from `mobile/docs/handbook/android-apk-release.md` (`pnpm --dir mobile build:app`) only after type-check passes. Do not use a production signing key in the repository or environment files.

**Smoke matrix:**

| Scenario | Expected result |
|---|---|
| No published version / current version is latest | No prompt; normal app use continues |
| Matching WGT | Prompt → download → SHA-256 pass → WGT install → app restarts on target version |
| WGT base mismatch | Backend returns FULL; Android full package path is used |
| Forced/minimum-supported update | Cancel is unavailable; failure is reported without silently continuing as “updated” |
| Bad digest or unavailable file | Installation is skipped; current version remains usable |
| Revoked/draft/channel-ineligible/rollout-ineligible release | `NONE`; no prompt |
| iOS or unsupported full-package platform | Clear external distribution guidance; no unsupported in-app install attempt |
| WeChat Mini Program/H5 | Existing platform-native update path remains unchanged |

### Task 6: Document release operation and handoff

**Files:**

- Update if needed: `mobile/docs/handbook/android-apk-release.md`
- Optional new operational note: `docs/plans/2026-09-22-mobile-app-update-integration.md` (this plan)
- If backend code changes are required: commit them inside the `fa-app` submodule and update the parent repository gitlink only after verification.

**Steps:**

1. Document the exact order: build package → compute SHA-256 → upload file → create draft `app_release` → create `app_release_package` → publish → call public check endpoint → install smoke test.
2. Record how to revoke a bad release and how to use `minSupportedVersionCode` for emergency forced full-package upgrades.
3. Record that generic `app_release` maintenance is currently not exposed by the existing `fa-app-pages` admin UI; decide whether operations will use API/SQL for now or create a separate admin feature request.
4. Mark the related plan/ADR as `🔍验证中` until the device smoke matrix passes; only then mark it `✅已完成`.

## Definition of done

- Production/test App-PLUS configuration has a valid `appCode`, API base URL, and synchronized app version values.
- The public check endpoint returns the expected manifest for the test release and `NONE` for ineligible clients.
- Android can complete WGT update and full-package fallback with SHA-256 verification.
- Failed download, verification, installation, cancellation, and unsupported-platform paths do not corrupt or block the current version.
- `pnpm --dir mobile type-check` passes; backend compile/tests and the agreed App-PLUS smoke matrix pass.
- The release operation and rollback procedure are documented, and no unrelated modules or old update APIs are changed.
