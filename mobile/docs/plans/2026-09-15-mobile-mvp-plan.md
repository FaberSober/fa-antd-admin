# 移动端 MVP 基础壳实施计划

> **For Codex:** 方案确认后，按本计划的实施顺序逐项执行并验证。

**Goal:** 建立独立的 uni-app 移动端宿主和可复用 Base Feature，完成账号密码登录、空白首页和用户信息展示，验证 Android、iOS、微信小程序三端基础链路。

**Architecture:** `mobile/` 是独立 uni-app 宿主，业务页面按 `mobile/src/features/*` 分包；每个 Feature 可作为 Git 子项目复用。MVP 直接复用现有 Portal 登录和用户信息接口，不新增业务表和后端业务模块。

**Tech Stack:** uni-app（Vue 3 + TypeScript + Vite）、Pinia、轻量自研组件；请求、存储和平台能力统一使用 uni-app API，不复用 Faui。

## 2. 当前 MVP 开发说明

### 2.1 mobile 宿主工程

- 创建 `mobile/` 独立前端工程，不加入现有 React/Faui 依赖。
- 保留宿主级 `App.vue`、`main.ts`、`pages.json`、`manifest.json` 和环境配置。
- 宿主只负责应用启动、Feature 注册、平台配置和全局生命周期。
- 使用 Vue 3、TypeScript、Vite、Pinia 和轻量组件方案。

### 2.2 Feature 分包与 Git 子项目

- Feature 目录统一放在 `mobile/src/features/`。
- 第一项 Feature 命名为 `fa-base-mobile`，作为可复用 Git 子项目。
- Feature 自己维护页面、组件、API、状态和类型，并提供页面清单。
- 宿主维护启用的 Feature 注册表；新增或移除业务只调整子项目和注册项。
- `pages.json` 必须在编译期完成页面注册，不使用运行时动态扫描。
- `fa-base-mobile` 的远程 Git 地址待确认后写入根目录 `.gitmodules`。

### 2.3 请求与会话

- 使用 `uni.request` 封装 GET、POST 和统一响应处理。
- token 保存到 `uni.setStorageSync`，请求头使用 `Authorization`。
- 统一附加客户端来源和版本信息，具体值由宿主环境配置提供。
- 收到 401 时清除本地会话并跳转登录页，避免页面自行重复处理。
- 不使用 `window`、`localStorage`、`FormData` 或浏览器 `File` API。

### 2.4 登录

- 使用账号密码登录，Android、iOS、微信小程序共用同一接口。
- 调用现有 `POST /api/portal/auth/login`。
- 登录成功后保存 token 和用户信息，并进入首页。
- 登录失败显示后端业务提示，不保留无效 token。
- 当前不接入微信 `wx.login`；原生微信登录放在未来版本。

### 2.5 空白首页与用户信息

- 登录后进入空白首页，不实现业务列表和复杂工作台。
- 首页展示用户姓名、账号、手机号、邮箱、头像和状态等基础信息。
- 调用 `GET /api/portal/account/me` 刷新当前用户信息。
- 提供加载中、请求失败和重新加载状态。
- 第一版不增加独立个人中心页面，用户信息直接展示在首页卡片中。

### 2.6 退出登录

- 调用现有 `GET /api/portal/auth/logout`。
- 无论服务端退出接口是否成功，都清理本地 token 和用户信息。
- App 重启时先检查本地 token，再决定进入首页还是登录页。
- 后续任意接口返回 401 时回到登录页。

## 3. 后续 Feature 规划

### 3.1 Base Mobile 内的建议收集

- 在 `fa-base-mobile` 内增加建议收集子目录和页面，不新增独立客户端子项目。
- 提供建议列表、详情和提交页面。
- 建议内容包括标题、分类、描述、状态、回复和截图附件。
- 截图使用 `uni.chooseImage` 和 `uni.uploadFile`，支持多张图片。
- 上传完成后业务数据只保存文件 ID。

### 3.2 Base 后台建议维护

- 在现有 `fa-base` 内增加建议收集子包、接口和数据访问层，不新增 `fa-suggestion` Java 模块。
- 在 `fa-base-pages` 内增加建议维护页面，不新增 `fa-suggestion-pages` 子项目。
- 支持建议列表、状态更新、回复记录和处理人信息。
- 状态记录和回复记录独立保存，不把所有回复覆盖在单个字段中。
- 新增数据库表时同时提供 MySQL 和 PostgreSQL 两套脚本。

### 3.3 消息通知 Feature

- 新增 `fa-message-mobile` 客户端子项目。
- 第一版采用前台刷新未读数和消息列表的方式验证闭环。
- 建议状态或回复变化时复用现有 `MsgHelper` 和 `base_msg`。
- 使用业务类型和业务 ID关联到具体建议详情。
- WebSocket、系统推送和厂商推送作为后续增强，不作为第一版前置条件。

### 3.4 Base 内部边界

- Base 继续作为公共基础模块，承载用户、文件、系统消息和轻量建议收集能力。
- 建议功能在 `fa-base`、`fa-base-pages`、`fa-base-mobile` 内分别保持独立的目录、API、类型和页面边界。
- Base 内部先按子域组织，后续只有在功能规模或复用需求明显增加时再拆成独立模块。
- 移动端建议路径建议使用 `fa-base-mobile/suggestion`，后台建议路径建议使用 `fa-base-pages` 的建议管理目录。

## 4. 实施顺序与验收

1. 创建 uni-app 宿主和基础环境配置。
2. 建立 Feature manifest、注册表和 `fa-base-mobile` 子项目路径。
3. 实现请求封装、token 持久化和统一 401 处理。
4. 实现登录页并接通现有 Portal 登录接口。
5. 实现空白首页和用户信息卡片。
6. 实现退出登录和 App 重启登录态恢复。
7. 配置 Android、iOS、微信小程序开发构建入口。
8. 使用测试账号完成三端启动、登录、首页、退出登录验证。

验收通过标准：

- 三端均可启动并访问后端。
- 登录成功后能进入首页并显示用户信息。
- App 重启后登录态行为正确。
- 登录失败、接口异常和 token 失效均有明确处理。
- 不新增建议业务表，不接入截图上传和消息中心。

## 5. 必要配置与待确认项

- `fa-base-mobile` 远程 Git 仓库地址。
- 开发、测试和生产 API 基础地址。
- Android/iOS 是使用 HBuilderX 打包还是后续接入 CLI/CI。
- 微信小程序 AppID 和合法 HTTPS 请求域名。
- 宿主项目名称、Logo、主题色和应用版本号。
- 是否需要在后续版本增加独立“我的”页面。

本计划默认使用账号密码登录、首页直接展示用户信息、轻量自研组件，并且不依赖 Faui。
